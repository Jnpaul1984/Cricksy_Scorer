## Proposed lifecycle specification — conditional on decisions

This model is a reviewable design, not a locked runtime policy. `not_started` is absence of a trial row. Readiness `not_ready | ready | data_unavailable` is derived from current bounded evidence and must never itself create a state row. After an approved explicit activation, durable states would be `active`, `exhausted`, `expired`, `revoked`, and `review_required`. The final names and access effects depend on T2, T5–T9.

| Transition | Conditional preconditions | Atomic outcome |
|---|---|---|
| `not_started → active` | Approved actor/event; active organization and exact Team; current five-match readiness `ready`; current pilot authority; no prior trial for chosen scope (T1/T2/T8/T9). | Record scope, actor, reason, activation time, five prerequisite source fingerprints, policy version, allowance `3`, and first audit event. No Game consumed. |
| `active → active` (one consumption) | Post-activation distinct Game; approved T3/T4 eligibility, trusted metadata and ledger; access and state revalidated; fewer than three committed consumption identities. | Insert one immutable Game consumption identity and audit event; derived count increases by one. Duplicate delivery of the same event returns the existing outcome. |
| `active → exhausted` | Exactly the third unique qualifying Game commits. | Insert its identity and terminal audit event in the same transaction. Final-game report access follows T6. |
| `active/exhausted → review_required` | Correction, undo, date/format change, or attribution conflict affects a prerequisite or consumed Game under T5. | Preserve original audit/consumption identity, record mismatch and block further consumption pending approved resolution. |
| `active → expired/revoked` | Owner-approved expiry/revocation rules (T7/T9). | Persist actor/reason/time where applicable; preserve the consumption ledger and decide read access per T6/T9. |

No transition is triggered by a page load, a readiness/report read, an API retry, or a Free scoring request merely because the Game exists. No historical Game is silently backfilled into a trial. An excluded/ambiguous candidate yields a safe unavailable/review state, not an assumed charge or a substitute Game. Trial status, if approved for staff display, would expose only state, `0–3` used/remaining counts, and policy-approved access window; no Game IDs, child/player identity, raw deliveries, audit actor IDs, or notes.

## Proposed transaction and idempotency contract

After the policy gate, design the migration so a trial row has a unique key for the approved scope and an explicit policy version. A separate append-only event/consumption ledger needs a unique `(trial_id, game_id)` consumption identity plus an idempotency key for the approved event type. Use PostgreSQL constraints as the final defense, not a preflight count alone. Activation must re-evaluate bounded five-match readiness. Each consumption operation must begin with the approved actor/access checks, lock the trial/scope row, verify the **frozen** prerequisite identities and their current revisions/digests without substituting newer matches, then validate the candidate Game under a consistent transaction view and insert the event/update state in one transaction. Two simultaneous Game completions must serialize; only the first three distinct qualifying Games may commit. A duplicate request must return the same outcome without an extra charge. A stale revision, changed prerequisite, unavailable evidence, exceeded workload bound, or lost grant/membership must fail closed before mutation. Choose an ordered, non-disclosing conflict response after T2–T9 are locked.

The five prior Game fingerprints are internal evidence only. Post-activation Game identity must come from frozen saved-Team attribution and trusted original format, never current `overs_limit`, fixture schedule, creation time, or player data. A candidate's date alone does not establish same-day order. Correction/undo policy must use compensating audit events rather than deleting a consumption row. A clean downgrade may remove an empty schema; a downgrade with any activation or audit history must refuse rather than erase it. No billing or future-paid table is part of this foundation.

## Threat analysis and implementation plan after approval

| Risk | Required control/test |
|---|---|
| Cross-tenant Team/Game or another organization's opponent | Exact organization and Team predicates in the service and DB keys; direct-service and route denial with no foreign identifiers/counts. |
| Grant, membership, role, or organization changes after activation | Revalidate at each access/transition; distinguish 403/404 per existing pilot contract; revoke/expire/inactivate tests for School and Club. |
| Duplicate, reordered, or concurrent events | Unique Game identity, idempotency key, row lock/transaction, real PostgreSQL two-writer test, and a fourth-Game rejection. |
| Edited date, format, ledger, or undo after a charge | Revision/digest check, immutable correction audit, approved T5 resolution, no silent refund or replacement. |
| Same-day chronology or historical import | T4 order evidence or review-required suppression; no Game-ID/time inference; no retroactive consumption. |
| Trial bypass through report/status reads | Read-only typed allowlist; no consumption on GET, retries, stale UI responses, or Free scoring paths. |
